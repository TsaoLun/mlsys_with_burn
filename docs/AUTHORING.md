# 写作与实验规范

## 章节结构

每章入口包含：

1. 为什么需要这一系统能力（OpenMLSys 式的问题，而不是框架功能清单）
2. 学习目标与先修知识
3. 框架无关的核心原理与成本模型
4. 产业中常见的对应物（一表即可）与 Burn 技术栈的实现落点
5. 可运行实验
6. 练习与延伸阅读（章末一句指向来源附录即可）

复杂章节可拆为独立小节，但入口必须说明建议阅读顺序。第 1 章可为 7 个
小节；第 2–9 章各 8 个小节。

项目自洽材料（证据标签总表、主题比较卡、逐文件对照导读、各章来源长文）
只写在附录 `appendix-scope-and-evidence.md` 与 `appendix-sources.md`，
不进入章首主路径。

## 表述要求

- 首次出现的术语给出中英文，例如“自动微分（automatic
  differentiation）”。
- 不把 API 形状描述成系统原理。
- 对性能结论说明硬件、后端、数据类型、形状和测量方法。
- 尚未实现或需额外环境的能力用分工表写出「系统需要 / 这里提供 / 应用要补」，
  不要用「未覆盖 / 不能外推 / 刻意不做」当章首主题。
- 源码路径绑定 `pins.toml` 的 commit。学习者正文用「本书所用版本」或链到
  [如何运行本书示例](../book/src/running-examples.md)；不要在章首讨论快照、
  证据或 CI（D025）。
- 证据标签与 C/S/R/L/E 仅出现在附录。实验节写「你会看到什么 / 这个实验停在哪」，
  不写验收口径。
- 不得把一次本地测量或模拟数字写成真实硬件或生产 runtime 结论；交代清楚
  硬件、后端、形状和同步即可，不必每段重复免责。
- 「固定 X」修饰语在全书前言或运行指南交代版本后，章内省略（D023/D025）。
- 结构关系图优先使用 `book/src/img/` 自制 SVG；`text` 围栏只用于
  代码轨迹、消息序列等以等宽文本为主的内容。新增 SVG 必须以 UTF-8
  写盘、读回比对并通过 XML 解析（见 svg-assets 检查）。

## GPU / 多后端三轨写法

GPU 与多后端在**主线同步介绍**，与默认可运行的 CPU 实验并行：

1. **原理轨**：并行层次、存储层次、占用、同步与数据搬运——可早讲、框架无关。
2. **源码轨**：按本书固定版本定位 Burn `Device`/dispatch、`burn-wgpu` /
   `burn-cuda`、CubeCL `CpuRuntime` / `WgpuRuntime` / `CudaRuntime` /
   `HipRuntime` 等入口；源码中有类型 ≠ 默认已测性能。
3. **实验轨**：默认 CPU（或已文档化的可选 `--features wgpu`）验证语义；
   不把无驱动环境上的失败写成正文必经步骤。

可选真机 / ONNX 跑通命令只写在 `docs/OPTIONAL_PROFILES.md` 与
`book/src/running-examples.md`，且不得进入默认 `make check`（D022）。

## 本章系统结论

每章练习页在「来源与改编」指针之前增加 `## 本章系统结论`（5–8 条），建议覆盖：

1. 本章解决的系统问题；
2. 关键抽象或成本模型；
3. 产业里常见的对应物（DDP、DataLoader、vLLM、调度器等，一句话）；
4. 行为落在 Burn / CubeCL 的哪一层、改它时先打开哪个 crate；
5. 实验让你看到什么；
6. 这个实验或模型回答不了什么（一条即可）。

## 练习体例

- 练习题标注难度：`【基础】`（概念回顾或与正文同构）、`【进阶】`
  （改示例、读固定源码或跨小节综合）、`【挑战】`（额外硬件、外部数据
  或开放设计）。
- 每题后可用 HTML `<details><summary>提示</summary>…</details>` 给出
  方向，指向正文小节、`examples/` crate 或书中给出的源码路径；
  **不提供完整参考答案**，避免把未验证路径写成标准答案。
- 提示必须题目专属（D023）：至少包含一个指向具体小节的 markdown
  链接、示例 crate 观察点或源码路径，外加一句实质性思考方向；禁止
  「回看第 N 章与本题对应的小节」这类零信息量套话，同一句提示不得在
  一章内复用。
- 【挑战】题须标明需要额外硬件、外部数据或自行设计，且不暗示本书默认
  CPU 示例已覆盖；正文不提 CI / release gate。

## 代码要求

- 正文通过 `{{#include ...}}` 引用 `examples/` 中的源码。
- 一个代码块只承载一个教学意图。
- 基础路径使用 CPU；平台专用示例必须标明软硬件前提。
- 示例测试数值、形状或可观察状态，不能仅验证“能够编译”。
- Python、C++、CUDA 或配置片段可在跨系统比较时保留，但不能冒充 Burn
  实现。

## 数学公式

- 行内公式使用 `$...$`，独立公式使用 `$$...$$`。`book.toml` 开启
  `mathjax-support`，并由 `book/theme/head.hbs` 为 MathJax 2 注入
  `tex2jax` 配置，使 `$`/`$$` 与官方 `\\(`/`\\[` 都能渲染（见 D019）。
- 不要把行内 `$...$` 拆到多行；跨行内容改用 `$$...$$`，否则分隔符配对
  容易把后续中文吞进公式。
- 数学片段中的下标符号写成 `\_`，让 Markdown 先保留 `_`，避免它把
  `\mathcal{L}_{...}`、`T_{\text{...}}` 等内容解析成 `<em>`。
- 独立公式的续行不要以 Markdown 列表标记 `+` 或 `-` 开头；使用
  `{}+`/`{}-` 等价的数学写法，避免生成 `<ul>`/`<ol>`。
- `make book` 后应检查生成 HTML：含公式页面必须加载 MathJax，且
  `head` 中存在 `inlineMath` 的 `$` 配置；公式内不应出现 `<em>`、
  `<ul>` 或 `<ol>`；页面正文不应再残留“裸美元符 + TeX 命令”的未渲染块。

## 参考文献页

外部论文、教材与官方文档集中在 `book/src/references.md`，按章分组，
每条附一句「它与正文的关系」。规则（D023）：

- 各章练习页的「延伸阅读」以一行链接指向该页对应章节锚点；正文点名
  论文（如 GPipe、ZeRO）时也应能在该页找到出处。
- 文献只作原理与产业背景延伸，不作为本书固定版本的能力证据；能力
  断言仍以固定源码与示例为准。
- 链接只使用有把握的 arXiv、DOI 或官方站点；不确定链接时给出
  「作者、题名、venue、年份」即可，不编造 URL。

## OpenMLSys 改编记录

各章文件级改编说明写入 `book/src/appendix-sources.md`（按章分节）；
章末练习页只保留一句指向该附录的指针。工程侧逐文件总账仍在
`planning/comparison/openmlsys-v1-crosswalk.md` 与
`planning/chapter-sources/`。

附录中的每章条目至少记录：

- 参考的 OpenMLSys 文件路径；
- 保留的通用概念；
- 被替换的框架专用论述；
- 新增的 Burn/Rust 内容；
- 复用图表及其修改情况。

直接或紧密改写的内容应就近署名。所有网络图片默认禁止使用，除非许可和
来源均已确认并随项目记录。

## 术语与地图

跨章统一用语与三张地图符号见 [`TERM_GLOSSARY.md`](TERM_GLOSSARY.md)。
新增正文时先查术语表，再写小节；不要在邻近章节引入同义反复的新叫法。
