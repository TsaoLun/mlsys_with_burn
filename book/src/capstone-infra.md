# 训练与服务成本实验

第 6 章把模型切到多张卡上，第 7 章把请求切进同一条 decode 步。两边问的
是同一类问题：**切开的对象是什么，同步或排队的代价落在哪一项**。本页
不训练新模型，只把已经能跑的两个虚拟时间实验放在一起读。

```text
cargo run -p ch06-parallel-strategies --locked
cargo run -p ch07-serving-queue-sim --locked
```

## 先看训练切分

`ch06-parallel-strategies` 打印四张整数表。读的时候只抓这几件事：

1. 环形 AllReduce 每设备发送 \(2(p-1)S/p\) 字节。\(p\) 从 4 到 32 时，
   这一项趋近 \(2S\)，但 α 步数从 6 涨到 62。小梯度、多卡时，延迟项会
   压过带宽项。
2. GPipe 空闲比例 \((p-1)/(m+p-1)\)。同样 4 个 stage，\(m=1\) 时空闲
   \(3/4\)，\(m=64\) 时变成 \(3/67\)。加 micro-batch 是在填气泡，不是
   在发明一种新并行。
3. 1F1B 把分母换成 \(2m+p-1\)，同一组 \((p,m)\) 下空泡更小，warm-up /
   drain 仍在。公式把每个 F/B 槽当成等长。
4. ZeRO-1 只把优化器状态除以 \(n\)；ZeRO-3 三份都除。省下的显存，下一
   次前向要用参数 AllGather 买回来。张量并行的一层 AllGather 是同一类
   \((p-1)S/p\) 流量，只是切的是隐藏维，不是状态。

这些数字解释切分对象与通信轮次。它们不是 NCCL 测量，也不是 Burn 已经
提供了 Megatron 调度。

## 再看服务队列

`ch07-serving-queue-sim` 在同一组混合长度请求上比较静态批、连续批和
分块 prefill。把这三列分开看：

| 指标 | 它在回答 | 常见误读 |
|---|---|---|
| 端到端延迟 | 从到达到最后一个 token | 把它当成 TTFT |
| TTFT | 用户等到第一个 decode token | 把它当成「模型算得快」 |
| TPOT | 首 token 之后每个后续 token 的间隔 | 忽略同一步里别人的大 prefill |
| 空转槽步 | 静态批里短序列在等最长序列 | 当成 KV 不够 |

连续批处理吃掉的是**长度方差**：短请求先走，新请求可以进正在进行的
decode 步。分块 prefill 吃掉的是**步内干扰**：一条 512 token 的 prompt
不再独占整整一步。KV 预算吃掉的是**并发上限**。三件事不要合成一句
「vLLM 所以更快」。

## 合在一起问

跑完两组输出后，用纸回答（不必改代码）：

1. 为什么环算法每设备字节几乎与 \(p\) 无关，而流水线空泡强烈依赖
   \(m/p\)？切开的对象分别是什么？
2. 把 \(p\) 从 8 加到 64，AllReduce 的 α 项与 ZeRO-3 的参数 AllGather
   哪一项先让小模型得不偿失？
3. 分块 prefill 改善的是在飞请求的 TPOT，还是新请求的 TTFT？什么时候
   更小的 chunk 反而让 TTFT 变差？
4. 若把第 6 章的张量并行组放进第 9 章「同节点最高带宽域」，它保护的
   是哪一张表里的哪一项？
