# 静态信息、Pass 与自动微分边界

## 1. 类型信息分布在不同阶段

第 2 章已经看到 `Tensor<D, K>`：秩和类别进入 Rust 类型，shape、dtype、
Device 在运行时确定。编译器还会推导更多局部事实，例如：

- 两个 shape 是否满足广播；
- 某个值是否为编译期常量；
- 某个 Tensor 是否只有最后一个使用者；
- layout/stride 是否允许向量化；
- 操作是否有副作用或可能改变别名；
- 某条设备指令是否支持当前 dtype。

不能把“Rust 编译通过”写成“所有 Tensor 条件都已静态证明”。反过来，
运行时检查也不表示 Rust 类型没有价值：它已经排除了错误秩和类别的部分
API 组合。

## 2. Pass 是带不变量的变换

一个 Pass 接收 IR，分析后返回等价 IR 或附加信息。常见前端优化包括：

- **常量折叠**：在编译期计算纯常量表达式；
- **常量传播**：把已知值传给后续操作；
- **死代码消除**（DCE）：删除结果不可观察的纯操作；
- **公共子表达式消除**（CSE）：复用等价计算；
- **代数化简**：在数值语义允许时使用恒等式。

Pass 顺序会影响结果。例如常量传播可能暴露新的不可达分支，随后 DCE 才能
删除。浮点优化还受 NaN、Inf、舍入和 fast-math 策略约束；看似熟悉的代数
恒等式不一定逐位等价。

OpenMLSys 对这些 Pass 给出通用介绍。本书保留原理，但不声称固定 Burn
Fusion 实现了全部传统编译器优化。Burn Fusion 的核心目标是发现可执行的
融合块和安全顺序，CubeCL 各 Compiler 再运行自己的低层优化。

## 3. Shape、dtype 与特化

动态信息可以有三种处理方式：

1. 保留为运行时参数，减少编译变体；
2. 进入编译键，生成特化 Kernel；
3. 只用于候选过滤和 launch 配置，不改变 Kernel 结构。

过度特化会造成 Kernel explosion 和缓存压力；特化不足会保留分支、动态
索引或低效布局。第 3 章实验中 `#[comptime] scale` 进入特化键，而 buffer
长度属于运行时元数据；但长度又影响 CubeDim 选择，因此仍可能改变编译键。

## 4. 自动微分不是一个普通优化 Pass

反向模式自动微分读取前向依赖并构造梯度计算。它可以实现为运行时 tape、
源到源变换或 IR 变换，但目标是产生导数程序，不是单纯让原程序更快。

固定 Burn 快照使用动态 autodiff tape；Fusion 则记录可延迟的 Tensor 操作。
两者可以叠加，却有不同生命周期：

- tape 保存反向所需节点和状态；
- Fusion OperationIr 服务于当前 stream 的优化与物化；
- `backward()` 沿 tape 生成/执行梯度；
- `Device::sync()` drain Fusion stream，但不等于执行 backward。

`detach()` 切断求导依赖，也不能被描述为“从 Fusion IR 删除节点”。第 2 章
已讲求导 API，本章只强调表示层边界。

## 5. 副作用和可观察行为

合法变换必须保持可观察语义。随机数、I/O、设备同步、原地更新和 host 回调
都会限制重排。即使两个算子数据依赖允许交换，随机数流或异常时刻也可能
改变。

Fusion 搜索不能只看数学公式；它还要尊重 Tensor 生命周期、读写状态和
stream 顺序。安全优化的第一条件是语义正确，其次才是减少 Kernel 和访存。
