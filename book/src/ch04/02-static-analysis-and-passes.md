# 静态信息、Pass 与自动微分边界

## 1. 类型信息分布在不同阶段

第 2 章已经看到 `Tensor<D, K>`：秩和类别进入 Rust 类型，shape、dtype、
Device 在运行时确定。编译器还会推导更多局部事实，例如：

- 两个 shape 是否满足广播；
- 某个值是否为编译期常量；
- 某个 Tensor 是否只有最后一个使用者；
- layout/stride 是否允许向量化；
- 操作是否有副作用或可能改变别名；
- 某条设备指令是否支持当前 dtype。

不能把“Rust 编译通过”写成“所有 Tensor 条件都已静态证明”。反过来，
运行时检查也不表示 Rust 类型没有价值：它已经排除了错误秩和类别的部分
API 组合。

## 2. Pass 是带不变量的变换

一个 Pass 接收 IR，分析后返回等价 IR 或附加信息。常见前端优化包括：

- **常量折叠**：在编译期计算纯常量表达式；
- **常量传播**：把已知值传给后续操作；
- **死代码消除**（DCE）：删除结果不可观察的纯操作；
- **公共子表达式消除**（CSE）：复用等价计算；
- **代数化简**：在数值语义允许时使用恒等式。

Pass 顺序会影响结果。用一段中性伪 IR 手推：

```text
v0 = const 2
v1 = add v0, v0      // 若已知为纯运算，可折叠为 const 4
v2 = mul x, v1
v3 = mul x, 4        // 与 v2 等价的候选
y  = add v2, 0       // 若加零可化简，y 可直接等于 v2
dead = mul v3, 0     // 若结果不可观察，DCE 可删除
return y
```

若先做常量折叠/传播，`v1` 变为 `4`，`y` 可能化简为 `v2`，随后 DCE 才能
删除 `dead`（以及不再被使用的 `v3`）。若先做 DCE 却尚未证明 `dead` 的
输入可消除，或尚未传播常量，删除机会更小。顺序不是风格问题，而是能否
暴露新的不可达或无用计算。

浮点优化还受 NaN、Inf、舍入和 fast-math 策略约束；看似熟悉的代数恒等式
不一定逐位等价。一个具体反例：`f32` 中
$(10^{16} + 1) - 10^{16} = 0$，而不是数学上的 $1$——大数吃掉了小数的
尾数精度，因此“先加后减同一常量可消去”这条中学恒等式对浮点 IR 是
**非法**变换；同理 $x + y = y + x$ 逐位成立，但
$(x + y) + z$ 与 $x + (y + z)$ 一般不逐位相等，重排归约顺序会改变
结果。Pass 作者必须明确自己工作在哪种数值语义下。

## 2.1 每个 Pass 都要写清楚的契约

阅读或设计 Pass 时，可以把它写成四元组：

```text
输入不变量 → 分析条件 → 输出不变量 → 不能变换时的处理
```

例如：

- **常量传播**要求定义值在当前控制流路径上唯一且无副作用；输出中每个
  替换使用仍保持类型、shape 和异常语义；无法证明时保留原值。
- **DCE**要求操作结果不可观察，且操作本身没有随机、I/O、同步或可能
  影响错误时序的副作用；删除后仍要保留被其他节点使用的输入定义。
- **CSE**要求两个表达式的操作、输入、dtype、layout 和相关控制状态都
  等价；若随机源、别名或浮点严格语义不同，就必须拒绝合并。
- **融合**要求中间值没有外部读取者、fuser 支持 shape/broadcast/layout/
  dtype，且生成 Kernel 的资源和同步成本可接受；不满足时回退到
  unfused operation。

这组契约解释了为什么“经典 Pass 名称存在”不等于“Burn 已实现
该 Pass”。教材可以用中性 IR 说明必要条件，但 Burn Fusion 是否执行
某个变换仍必须回到 fuser、策略和测试源码核对。

### 亲手写一个 Pass

上面的契约可以在两百行代码里全部落地：本章配套实验
`examples/ch04-mini-pass-pipeline` 用一个五算子表达式 IR 实现了
常量折叠、DCE 和 CSE，每个 Pass 的测试都断言「优化前后输出按位
一致」；还有一个**故意非法**的 fast-math 消去改写，正是上文
$(10^{16}+1)-10^{16}$ 反例的可运行版——同一改写在小常量上看似
无害，换成大常量后 `x = 1` 的结果从 $0$ 变成 $1$，测试用
`assert_ne!` 把「样例碰巧通过不等于 Pass 合法」钉在代码里。代码
与运行输出见[实验小节](07-fusion-inspector-lab.md)第 10 节。

OpenMLSys 对这些 Pass 给出通用介绍。本书保留原理，但不声称 Burn
Fusion 实现了全部传统编译器优化。Burn Fusion 的核心目标是发现可执行的
融合块和安全顺序，CubeCL 各 Compiler 再运行自己的低层优化。

## 3. Shape、dtype 与特化

动态信息可以有三种处理方式：

1. 保留为运行时参数，减少编译变体；
2. 进入编译键，生成特化 Kernel；
3. 只用于候选过滤和 launch 配置，不改变 Kernel 结构。

过度特化会造成 Kernel explosion 和缓存压力；特化不足会保留分支、动态
索引或低效布局。第 3 章实验中 `#[comptime] scale` 进入特化键，而 buffer
长度属于运行时元数据；但长度又影响 CubeDim 选择，因此仍可能改变编译键。

## 4. 自动微分不是一个普通优化 Pass

反向模式自动微分读取前向依赖并构造梯度计算。它可以实现为运行时 tape、
源到源变换或 IR 变换，但目标是产生导数程序，不是单纯让原程序更快。

Burn 使用动态 autodiff tape；Fusion 则记录可延迟的 Tensor 操作。
两者可以叠加，却有不同生命周期：

- tape 保存反向所需节点和状态；
- Fusion OperationIr 服务于当前 stream 的优化与物化；
- `backward()` 沿 tape 生成/执行梯度；
- `Device::sync()` drain Fusion stream，但不等于执行 backward。

`detach()` 切断求导依赖，也不能被描述为“从 Fusion IR 删除节点”。第 2 章
已讲求导 API，本章只强调表示层边界。

## 5. 副作用和可观察行为

合法变换必须保持可观察语义。随机数、I/O、设备同步、原地更新和 host 回调
都会限制重排。即使两个算子数据依赖允许交换，随机数流或异常时刻也可能
改变。

Fusion 搜索不能只看数学公式；它还要尊重 Tensor 生命周期、读写状态和
stream 顺序。安全优化的第一条件是语义正确，其次才是减少 Kernel 和访存。
