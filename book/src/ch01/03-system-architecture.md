# 从编程接口到硬件

机器学习系统可以被理解为一组逐层降低抽象的转换和运行机制。实际项目的
边界并不总与下图完全一致，但这张地图能帮助我们判断一个问题应在哪一层
解决。

```text
模型与训练程序
  │  编程接口、Module、Tensor、优化器
  ▼
张量执行与 autodiff tape
  │  Device、dtype、eager 前向、反向依赖
  ▼
Burn IR / Fusion 计划
  │  分析、融合、布局和算子选择
  ▼
CubeCL / CubeK Kernel
  │  Scope → KernelDefinition → JIT / 自动调优
  ▼
设备 Runtime（CPU / GPU / WebGPU / 远程）

数据管道 ─────► 训练执行 ─────► 状态与模型部署
                     │
                通信与集群系统
```

术语与三张地图的固定叫法见仓库 `docs/TERM_GLOSSARY.md`。

## 编程接口

编程接口把用户意图转换为系统可执行的对象。传统生态常以 Python 提供高层
接口，再由 C++ 或设备语言实现底层。Burn 把 Rust 作为一等用户接口和系统
实现语言，但底层仍可能调用驱动、编译器和外部库。

统一语言减少了部分 FFI 边界，却没有消除分层：易用的模型 API、高效的张量
分派、设备 Kernel 与驱动仍承担不同职责。Rust 的价值在于让这些边界更多地
以 trait、类型和显式所有权表达。

## 张量执行与计算表示

张量封装多维数据及其操作。执行一个张量运算时，系统至少要确定：

- 数据位于哪个设备；
- 使用哪种元素类型和内存布局；
- 对应后端是否支持该操作；
- 操作立即执行、被异步提交，还是先记录以便优化；
- 是否需要为反向传播保存信息。

“计算图”是表示操作及依赖的一种方式，但不是所有框架都只有一张静态图。
Eager 执行可以在程序运行时逐个分派操作；autodiff tape 记录反向依赖；
Fusion 把一段操作注册为 Burn IR 后再搜索执行计划。第 2 章把这三种表示
分开定义，避免统称为单一“Burn 计算图”。

## 编译器与运行时

编译器中间表示（intermediate representation，IR）让系统能够在不直接
操作用户源码的情况下分析和改写计算。常见变换包括：

- 合并多个逐元素操作，减少 Kernel 启动和中间内存；
- 根据形状与硬件选择矩阵乘算法；
- 改变布局或向量化方式；
- 安排内存复用和异步执行。

运行时负责设备发现、内存分配、Kernel 提交、同步与错误传播。编译器生成
的程序最终仍需要运行时和硬件驱动完成执行。

## 异构设备

CPU 适合控制流、数据预处理和低并行度工作；GPU 等加速器擅长规则、密集的
并行计算。真实应用往往同时使用二者，因此数据移动和同步可能比算术本身更
昂贵。

设备差异不仅是速度差异。支持的 dtype、最大内存、同步语义、编译方式和
Kernel 能力都可能不同。框架应提供统一语义，同时允许后端明确拒绝不支持的
组合，而不是静默产生错误结果。

## 横跨执行路径的系统

数据处理、训练状态、部署和分布式通信并非简单地位于某一层“下方”：

- 数据管道持续向训练执行供给批次；
- 自动微分与优化器改变模型状态；
- 检查点把内存中的参数编码为持久格式；
- 模型导入需要在不同框架语义之间转换；
- 分布式通信穿过张量、设备、进程和网络边界；
- 集群调度决定任务最终能获得哪些硬件。

因此调试机器学习系统时，必须沿端到端路径寻找瓶颈和语义偏差。只优化一个
Kernel，不一定能改善被数据读取限制的训练吞吐；只提升平均吞吐，也不一定
能满足在线服务的尾延迟要求。
