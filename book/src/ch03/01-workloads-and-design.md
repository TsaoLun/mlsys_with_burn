# 工作负载与加速器设计

## 1. 从算子观察负载

训练和推理虽然目标不同，热点却常落在少数算子族：

- 矩阵乘和卷积执行大量乘加；
- attention 同时包含矩阵乘、归一化与大规模中间数据；
- 归约、归一化和逐元素算子计算较少，却需要读写大量元素；
- embedding、索引和通信常受不规则访存或网络限制。

因此“每秒浮点运算更多”不是完整答案。系统必须同时考虑可用并行度、数据
搬运量、同步和启动开销。小 Tensor 即使总运算量不大，也可能因为一次
Kernel launch 或一次设备同步而变慢。

## 2. 三个基本量

### 并行度

若一个输出元素可以独立计算，系统可以把许多元素分给不同处理单元。并行度
不足时，再多硬件单元也会空闲；数据依赖或全局同步会缩小可并行区域。

### 数据复用

矩阵乘中的一个输入元素会参与多个输出。若每次使用都从高延迟内存重读，
计算阵列就会等待。把一块数据暂存在更近的存储层，可用有限容量换取复用。

### 计算强度

计算强度（arithmetic intensity）可粗略写为：

$$
\text{AI}=\frac{\text{执行的运算量}}{\text{从目标存储层搬运的字节数}}。
$$

低计算强度算子通常受带宽限制，高计算强度算子更可能受计算吞吐限制。
分界点由具体设备的峰值计算/带宽比决定，这就是 roofline 模型的核心直觉。
峰值只是上界，访存不连续、占用率不足和依赖链仍会降低实际性能。

用两个贯穿本章的例子把上式算出数值。本章实验的 `scale_kernel` 是逐元素
缩放：每个元素 1 次乘法，同时从全局内存读 4 字节、写 4 字节，因此

$$
\text{AI}\_{\text{scale}} = \frac{N\ \text{FLOP}}{8N\ \text{字节}}
= 0.125\ \text{FLOP/字节},
$$

与 $N$ 无关——它在几乎任何设备上都注定受带宽限制，增加算力毫无帮助。
相反，$1024 \times 1024 \times 1024$ 的 GEMM 约有 $2N^3$ 次运算，只读
$2N^2$、写 $N^2$ 个 `f32`：

$$
\text{AI}\_{\text{gemm}} = \frac{2N^3}{12N^2} = \frac{N}{6}
\approx 171\ \text{FLOP/字节},
$$

比逐元素算子高约三个数量级。给定设备的 roofline 拐点
$I^* = P\_{\max}/B\_{\max}$ 落在这两个数之间的任何位置，结论都一样：
scale 在带宽屋顶下，GEMM 在计算屋顶下。这就是“先算强度、再谈优化”的
意义——对 `scale_kernel` 讨论占用率和矩阵指令是无效优化，对 GEMM 只
减少指令数而不增复用同样无效。

## 3. 通用性、能效与可编程性

CPU 以复杂控制、低延迟和通用性见长；GPU 用大量较简单的执行单元换取并行
吞吐；领域专用加速器（domain-specific accelerator, DSA）进一步固定
数据流或数值格式以提高能效。越专用的硬件通常越难覆盖快速变化的模型。

软件抽象同样存在取舍：

1. **算子库层**最容易使用，也最能复用专家优化；
2. **Kernel 语言层**允许表达新的算法和融合，但要求理解拓扑、存储与同步；
3. **指令/内建层**可直接使用矩阵单元等特性，却最依赖设备能力。

Burn 技术栈并不消除这些层，而是让它们共享 Rust 工具链：

```text
Burn Tensor API
    ↓
burn-cubecl：Backend、调度、fallback 与 autotune
    ↓
CubeK 高性能算子  +  自定义 CubeCL Kernel
    ↓
CubeCL Runtime / Compiler
    ↓
CPU、WGPU、CUDA、ROCm 等具体 Runtime
```

这里的后端集合受 Cargo feature、平台和固定版本限制；“同一种 Kernel
语言”不等于“所有设备支持相同指令和性能”。

## 4. 正确性、可移植性与性能

加速器程序至少要分别回答三个问题：

- **正确性**：索引、shape、边界和同步是否满足算法语义？
- **可移植性**：目标 Runtime 是否支持 dtype、plane 操作或矩阵指令？
- **性能**：当前 shape 和设备上，这个策略是否优于其他实现？

CPU Runtime 很适合验证前两个问题中的一部分，但不能回答 GPU 的合并访存、
占用率和矩阵单元吞吐。后续实验会刻意保持这条边界。
