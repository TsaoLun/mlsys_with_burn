## Burn 固定快照核验

### 手写训练循环与优化器

- `burn/crates/burn-train/src/learner/train_val.rs`
  定义 `TrainStep`、`InferenceStep`、`TrainOutput` 和默认的
  `optimize`/`optimize_multi` 边界。训练 step 自己实现前向、反向和
  `GradientsParams` 构造；`LearnerModel` 还必须是 `AutodiffModule`。
- `burn/crates/burn-optim/src/optim/module/module_optimizer.rs`
  将参数按 `ParamId` 映射到动态 optimizer，提供单设备
  `step` 和多设备 `step_multi`，并把 optimizer state 序列化为
  `OptimizerRecord`。
- `burn/crates/burn-optim/src/optim/sgd.rs`、`adam.rs` 和
  `lr_scheduler/module_lr_scheduler.rs`
  验证了 SGD/Adam、参数组、梯度裁剪和可保存的 learning-rate scheduler
  状态。示例实验使用固定 CPU 路径的 SGD，不把收敛结果外推成性能结论。

### `burn-train` 训练环境

- `burn/crates/burn-train/src/learner/base.rs`
  中的 `Learner` 组合 model、`ModuleOptimizer` 和
  `ModuleLrScheduler`；它公开 `train_step`、`optimizer_step`、
  `optimizer_step_multi`、`fork` 和状态加载。
- `burn/crates/burn-train/src/learner/supervised/paradigm.rs`
  中的 `SupervisedTraining` 负责 dataloader、metric、renderer、epoch、
  checkpointer 和 training strategy 的装配。
- `burn/crates/burn-train/src/learner/supervised/strategies/single/epoch.rs`
  核验了单设备循环顺序：读 batch → `lr_step` → `train_step` →
  gradient accumulation/optimizer step → metric event。
- `burn/crates/burn-train/src/checkpoint/base.rs`、`file.rs` 和
  `learner/base.rs`
  核验了 module、optimizer 和 scheduler 分开保存为 device-free
  burnpack record；加载后 model 使用已有参数设备，optimizer state 在下一步
  按参数设备迁移。

### 本机多设备与 DDP

- `burn/crates/burn-train/src/learner/supervised/strategies/base.rs`
  暴露三类 `ExecutionStrategy`：
  `SingleDevice`、`MultiDevice(Vec<Device>, MultiDeviceOptim)` 和
  `DistributedDataParallel { devices, context }`。
- `multi/strategy.rs`、`multi/epoch.rs` 和 `learner/train.rs`
  核验了 `MultiDevice` 的本机语义：使用 `split_dataloader` 为每个设备
  建立 loader，训练 worker 每设备一个，`OptimMainDevice` 把梯度迁回主设备，
  `OptimSharded` 以 `(GradientsParams, Device)` 交给
  `ModuleOptimizer::step_multi`。这不是跨节点协议。
- `strategies/ddp/README.md`、`ddp/strategy.rs`、`ddp/worker.rs` 和
  `ddp/epoch.rs`
  核验了 DDP 的范围：每个本地设备一个线程/worker，各 worker 拥有模型副本，
  反向后通过 all-reduce 同步梯度；第一台设备负责验证、事件处理和主结果。
  用户必须在每个节点启动 DDP，并保证 collective 配置一致。
- `burn/crates/burn-tensor/src/tensor/distributed.rs` 的
  `DistributedContext` 负责启动/关闭通信协调器，`all_reduce` 返回必须在
  `resolve` 或安全条件下 `assume_resolved` 后使用的 `CollectiveTensor`。
- `burn/crates/burn-autodiff/src/distributed.rs`、`ops/distributed.rs`、
  `burn-backend/src/backend/distributed/{api,client,server,ops}.rs`
  核验了梯度同步机制：模型参数先通过 `set_distributed` 注册，autodiff
  在反向结束时提交 tensor，后端 server 等到所有设备的参数/梯度到齐后调用
  backend `all_reduce`，最后以 collective sync 作为可用边界。
- `burn/crates/burn-flex/src/ops/transaction.rs` 明确说明 Flex 使用默认
  `DistributedOps`，不支持 collective operations；因此 CPU Flex 不能作为
  本章 DDP 的运行验证路径。`burn-cubecl/src/ops/distributed.rs` 提供
  CubeCL 的 all-reduce 入口，而固定快照中 CUDA server 使用 NCCL；是否可用
  仍取决于后端、运行时和设备数。

### 通信 crate 的边界

`burn/crates/burn-communication/` 提供 protocol/channel、WebSocket 和
tensor data service 等网络传输抽象，但固定 `burn-train` 的 DDP 梯度同步通过
backend `DistributedOps`/collective 路径完成。不能把 data service 或 remote
tensor transfer 直接称为参数服务器，也不能从这些接口推出跨节点容错、作业
调度或 checkpoint 共识。

## 能力与限制清单

| 结论 | 证据级别 |
|---|---|
| 可以手写 CPU autodiff 训练循环并使用 `burn-optim` 更新参数 | 示例测试 + `train_val.rs`/`module_optimizer.rs` |
| `burn-train` 提供指标、日志、检查点和单设备训练装配 | 固定源码核验；不等于本章实验覆盖全部 UI |
| `MultiDevice` 是同一进程内按设备切分 loader 的本机策略 | `multi/strategy.rs`、`split_dataloader` |
| DDP API 有模型副本、梯度 collective 和节点配置责任 | `ddp/README.md`、`ddp/*`、`DistributedContext` |
| Flex CPU DDP 可在本机运行 | **不成立**；固定源码明确 Flex 没有 collective 实现 |
| Burn 固定快照提供参数服务器、流水线并行、跨节点容错和调度 | **未核验/不承诺** |

## 实验规划

新增 `examples/ch06-training-loop`，采用固定的小型线性回归数据：

```text
Tensor batch → Linear forward → MSE loss → backward
           → GradientsParams → SGD step → 记录 loss
```

实验只使用 `Device::flex().autodiff()`，测试以下可观察不变量：

1. 若干步 SGD 后最终 loss 小于初始 loss；
2. 参数发生变化，且训练过程没有依赖随机 batch 顺序；
3. 主程序打印每一步 loss，读者可以观察训练循环而不是只看到“编译通过”。

实验不测试 Flex DDP、网络通信、模型/流水线并行或吞吐扩展；这些边界在
正文和练习中明确标出。
