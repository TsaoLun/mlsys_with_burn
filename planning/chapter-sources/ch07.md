## `burn-onnx` 固定快照核验

### 仓库关系

`pins.toml` 中：

- `burn-onnx` 仓库 revision 为
  `af2dfb43af43bf363dc2d7d858d933d86e2a65a8`；
- `relationships.burn_onnx_burn_rev` 为
  `78f10aec1ca6c6ffb1edd17a0fa131ae59ad5403`；
- `burn-onnx/Cargo.toml` 的 workspace dependency 确实把 `burn`、
  `burn-flex`、`burn-store` 指向 `78f10aec...`，而不是项目主线的
  `976aa9c...`。

因此本章不把本地 `burn-onnx` mirror 接入根 workspace，也不把由旧 Burn
生成的 model 类型与当前 Burn 类型混用。两套 revision 的 crate 名称相同
并不意味着其 `Tensor`、`Module` 或 `BurnpackStore` 类型可以互换。

### `ModelGen` 与生成物

固定 `burn-onnx/crates/burn-onnx/src/model_gen.rs` 和 `burn/graph.rs`
核验了转换路径：

1. `OnnxGraphBuilder` 解析 ONNX 文件并可执行 graph simplification；
2. ONNX nodes 注册到 `BurnGraph`，再生成可读、可修改的 Rust source；
3. 节点中的常量/权重收集为 `.bpk` Burnpack 文件；
4. 默认 `LoadStrategy::File` 生成 `from_file`、`from_bytes` 和
   `Default`；
5. `Embedded` 生成 `include_bytes!` 对齐的静态权重和 `from_embedded`；
6. `Bytes` 只生成 `from_bytes`，适合调用者自己提供内存中的权重；
7. `None` 不生成内置权重加载器，调用者必须自行处理状态。

`ModelGen` 还提供 `simplify`、`partition`、development debug files 和
CLI `onnx2burn` 入口。代码生成时对不支持或语义不兼容的节点仍可能失败；
README 的“支持 operator”列表不能替代本固定 revision 的具体模型验证。

### ONNX 的验证边界

`burn-onnx` 仓库有 `examples/onnx-inference` 和 model-checks，验证方式
包括生成 Rust、加载 Burnpack 以及与 ONNX Runtime reference 比较。它们
属于 `burn-onnx` 自己的旧 Burn workspace，不能直接作为根 workspace 当前
Burn 的编译证据。本章只复述其源码结构，不把未在本项目运行的模型导入
结果写成已验证实验。

## Burn Record 与 Burnpack

### 核心 `ModuleRecord`

固定主线 `burn-core/src/store/mod.rs` 定义了轻量的 `ModuleRecord`：

- `Module::into_record` 遍历 module 参数，保存 path、`ParamId`、shape、
  dtype 和 tensor bytes；
- `ModuleRecord::into_bytes/from_bytes` 使用 Burnpack 内存表示；
- `Module::try_load_record` 返回 `RecordError`，默认校验缺失参数和 shape；
- `Module::load_record` 是校验失败时 panic 的便利入口；
- `DTypePolicy::FromRecord` 是默认行为，另有 `CastToModule`；
- 恢复时保留记录中的 `ParamId`，这对 optimizer state 的关联很重要。

这是一种模型参数状态格式，不包含完整的服务路由、预处理契约、模型版本
策略或安全密钥。当前实验只依赖它，因此可以在 CPU 上验证 export/load 和
推理输出的等价性。

### 可选 `burn-store`

固定 `burn-store` 提供更丰富的 `ModuleSnapshot`/`ModuleStore`：

- `BurnpackStore`：带元数据、适合 Burnpack tensor snapshots；
- `SafetensorsStore`：文件/内存、lazy snapshot、过滤和 key remapping；
- `PytorchStore`：在启用对应 feature 时读取 PyTorch 状态；
- `PyTorchToBurnAdapter`/`BurnToPyTorchAdapter`：例如 Linear 转置和
  normalization 参数重命名；
- `HalfPrecisionAdapter`/`FloatCastAdapter`：保存或加载时的 dtype 转换。

`burn-store` 的 feature、文件 I/O、mmap 和 adapters 是部署工具，不应和
核心 `ModuleRecord` 的最小 API 混称。精度转换也不是量化精度/误差评估；
必须另做数值校准。

## Remote、WASM 与 no_std

### Remote execution

固定 `burn-remote`/`burn-tensor` 源码核验：

- `burn` 的 `remote` feature 打开远程 client，`remote-server` 打开
  server，`remote-websocket` 保留兼容 WebSocket；
- 新路径以 Iroh endpoint/peer 为主，客户端构造 remote `Device`，计算
  operation 通过 remote backend/router 发给 compute peer；
- Remote server host 一个具体 backend 的 device 列表，可注册 typed custom
  operation；
- 同一进程内设备有 fast path，跨 peer tensor transfer 使用认证能力；
- `fusion` feature 可以在 remote backend 上缓存重复 operation groups，
  但这不是模型文件转换或 HTTP inference API。

`burn-remote` README 明确把 endpoint identity、relay policy、discovery、
authorization 和 fleet policy 留给应用；Remote 不自动提供租户、认证、
调度、计费、模型版本或故障转移。

### WASM/no_std

- `burn-core`、`burn-tensor`、`burn-store` 和 `burn-onnx` 的部分生成物可
  以 `no_std`/`alloc` 方向组织；
- `LoadStrategy::Embedded` 使用对齐的 `include_bytes!`，`Bytes` 使用内存
  输入；`File` 生成代码显式需要 `std::path::Path`；
- `burn-tensor` 的 Iroh remote client 在 WASM 上提供异步连接入口，因为
  浏览器线程不能阻塞；remote server 的 native 启动函数则有
  `not(target_family = "wasm")` 条件；
- WASM 仍需要目标后端（例如 WebGPU/remote）和浏览器构建工具，`no_std`
  并不等于“任何 backend 或文件 API 都可用”。

`burn-onnx` 的 converter crate 本身依赖 `std`、`burn-store` 和 ONNX parser
工具；“生成的模型可以选择 no_std 友好加载方式”与“转换器本身在
no_std 目标运行”是两个不同命题。

## 能力与限制清单

| 结论 | 证据级别 |
|---|---|
| 主线 Burn `ModuleRecord` 可在内存中 round-trip 参数并恢复 `ParamId` | 固定源码 + 本章 CPU 实验 |
| `burn-onnx` 可生成 Rust source 和 Burnpack loader 变体 | 固定 `af2dfb...` 源码核验 |
| 当前根 workspace 可直接把固定 `burn-onnx` 作为同一 Burn 类型依赖 | **不成立**；其 manifest pin 到 `78f10a...` |
| `burn-store` 支持 snapshot、过滤、remap、SafeTensors/PyTorch adapters | 固定源码核验，具体格式需启用 feature |
| Remote 可把 Tensor operations 发送给 Iroh/WebSocket compute peer | 固定源码核验；需要网络和 server |
| Remote 自动提供生产模型服务、鉴权、调度和容错 | **不承诺** |
| Burn 固定快照已提供通用量化/剪枝/蒸馏流水线 | **未核验/不承诺** |

## 实验规划

新增 `examples/ch07-record-roundtrip`，不下载 ONNX、不接入旧 Burn 依赖，
使用当前根 workspace 的 `burn` 和 Flex CPU：

```text
Linear model
    ├── forward(input) → reference output
    ├── Module::into_record → in-memory Burnpack bytes
    ├── ModuleRecord::from_bytes
    └── fresh model::try_load_record → restored output
```

测试断言：

1. record 包含预期数量的参数 tensor；
2. 还原模型与 reference 的输出 shape 相同；
3. 输出最大绝对误差在 CPU 浮点容差内；
4. `ModuleRecord` round-trip 不依赖文件、网络或 proprietary driver。

该实验验证的是参数 artifact 的加载，不是 ONNX importer、Remote server 或
浏览器部署的端到端证明。

## 改编说明

- 保留 OpenMLSys 的模型转换、图优化、压缩、推理指标和安全威胁模型；
- 用 `ModelGen`/ONNX graph → Rust source → Burnpack、`ModuleRecord`、
  `ModuleSnapshot`、Remote `Device` 和 target-specific loading 重写；
- 将算子融合与编译器优化的细节链接回第 4 章，不重复宣称部署阶段一定
  发生某个后端优化；
- 不复制 v1 的 MindSpore/PyTorch/ARM 汇编代码、图片和硬件性能数字；
- 不把模型文件保护、TLS/Iroh transport、访问授权和服务治理混成同一
  “模型安全”开关。

## Crosswalk 与证据状态

逐文件对照见 [`../comparison/openmlsys-v1-crosswalk.md`](../comparison/openmlsys-v1-crosswalk.md)
的“模型部署”段。主线 `ModuleRecord`/Burnpack round-trip 属于
`源码核验 + CPU 可运行验证`；artifact manifest、checksum、rollback 和
动态 batching 属于 `协议/成本模型`；burn-onnx 旧 revision、真实 ONNX
导入和服务治理标为 `可选平台实验/明确未覆盖`。

P1 新增的 `ch07-record-roundtrip` contract harness 检查稳定 checksum、
artifact version/rollback 和同 shape dynamic batching；它与主线
`ModuleRecord` round-trip 一样是 CPU/协议证据，不替代 burn-onnx 的
旧 revision ONNX fixture 或 HTTP 服务。
